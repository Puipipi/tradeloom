## 一、决策记录：v0.1 → v0.2 改了什么

| 项 | v0.1 | v0.2 | 为什么改 |
|---|---|---|---|
| Agent 数量 | 3 个智能体（Curator / Composer / Pricer）+ 主控 | **1 个主 Agent + 2 条工作流 + N 个 Python 工具** | 6 周里，多 Agent 的协调与评测成本吃掉的是"能跑通"这件事；三个功能型 Agent 本质是三条工作流 |
| 报价模块 | 报价陪跑：区间 + 依据 | **降级为「整理已确认价格 + 区间展示」** | 没有 30 单真实数据时，自动定价是负分；先把"价格不乱"做对 |
| 核心叙事 | 样品图 → 画册页 + 报价单 | **同一份已确认产品资料 → 多个互不矛盾的文件** | 只讲故事容易变演示；"改一处、全部文件跟着变"才是产品 |
| 交互形态 | AgentArts Demo 页面 | **轻量网页工作台（三区）+ AgentArts 作为大脑** | 赛题要"可视化 Demo 页面 + 可在线交互"，纯对话页撑不住"确认与版本" |

**但 v0.1 的两条没变**：① 人拍板、依据可追溯；② 每个功能对着真实死线验收。

## 二、初版做什么（v1，2 周内能演）

**一句话**：上传一批产品照片 + 现有商品表 → 输出「英文目录草稿（印刷规格 PDF）」+「样品打包核对表」+「待确认清单」；**只认已确认数据，缺的问你，原图不改。**

| 做 | 具体 |
|---|---|
| 导入 | 商品表（xlsx/csv）+ 图片批次（≤10 张/批，分批进） |
| 归一 | 货号、品类、材质、尺寸、颜色、单位、价格 → 统一字段 |
| 匹配 | 图片与货号的**候选**匹配（相似度只提候选，绝不判定） |
| 找问题 | 缺图、缺规格、重复货号、单位不明、图文不一致 → 逐条待确认 |
| 确认 | 网页表格里改，保存为 `version N`，记录是谁改的 |
| 生成 | 目录草稿 PDF（过 8 项印刷校验）+ 打包核对表 |
| 一致性 | 改一个字段 → 标出受影响的文件 → 重生成 |
| 交付校验 | 文件齐、页数够、规格过检 |

| 不做（写进"未来工作"） | 原因 |
|---|---|
| AI 自动定价、报"客户能接受的最高价" | 数据不够时是负分 |
| 采购 / 生产日报 / 财务 | 另一套产品 |
| 岗位式多 Agent（销售 Agent、采购 Agent 互相开会） | 现在还不知道每个岗位的真实边界，先造组织架构没有依据 |
| 账号体系、权限、审计 | 单人使用足够，评委看的是闭环 |

## 三、那个"工作台"到底能不能做

能，但要先说清"哪一种工作台"。三种目标，成本差一个数量级：

| 级别 | 长什么样 | 工期 | 结论 |
|---|---|---|---|
| **A 演示级** | 一页能点通：上传 → 确认 → 生成 → 下载，数据可预置 | 约 1 周 | 6 周内必达 |
| **B 可用级** | 真实上传、真实编辑、真实生成、版本可回退；单用户、单机/单容器部署 | 约 3–4 周 | **6 周内的上限，也是我们要交的东西** |
| **C 产品级** | 多用户、权限、审计日志、对象存储、队列、监控、计费 | 3 个月起 | 不做，也别在答辩里暗示能做 |

**我的判断**：B 级可以，而且不难——它的本质是「表格编辑 + 文件预览 + 任务状态」三件事，没有算法难点，难在交互细节的量。所以它必须排在 L1（文件真的能生成）之后，否则就是在给一个不存在的后端做界面。

页面只有三个区，多一个都不加：

| 区域 | 第一版要有的 | 不要有 |
|---|---|---|
| 任务与文件 | 新建任务、上传、进度、失败原因与重试 | 甘特图、看板拖拽 |
| 产品与确认 | 产品卡、图片对照、字段来源、缺项提示、编辑与确认 | 复杂筛选器、批量规则引擎 |
| 成果 | 预览、版本记录、审核状态、导出 | 在线协作评论 |

## 四、能不能一步一步做到：五级阶梯，每级都有门

```dsh-ui
{"title":"五级阶梯：每一级不通过就不进下一级","gap":14,"items":[{"type":"steps","steps":[{"title":"L0 闭环验证（3–5 天）","desc":"比赛账号里跑通：模型调用 → 自定义工具被真实调用（GET/POST 已通）→ 生成一个真能打开的文件 → 后端能调已发布应用。门：每一步都有截图或日志"},{"title":"L1 文件真能生成（约 1 周）","desc":"命令行/工作流里跑通：商品表 + 20 张图 → 目录草稿 PDF + 核对表。门：字段正确率 ≥90%（20 张里错 ≤2 张）、PDF 过 8 项校验"},{"title":"L2 工作台骨架（约 1 周）","desc":"上传 → 确认 → 生成 → 下载 四步走通。门：队友不看说明能自己跑完一遍"},{"title":"L3 一致性闭环（约 1 周）","desc":"改一个字段 → 标出受影响文件 → 重生成 → 版本记录。门：改一处，引用处全部更新，无一遗漏"},{"title":"L4 评测与打磨（约 1 周）","desc":"20 图 / 20 单回测，失败重试，成本统计，视频与文档。门：指标表有数（好看难看都要有数）"}]}]}
```

总工期约 5–6 周，正好卡在初赛材料提交前。**任何一级延期，砍的是下一级的功能，不是这一级的验收标准。**

## 五、平台硬约束（写进代码之前就要知道）

| 约束 | 影响 | 应对 |
|---|---|---|
| 工作流开始节点单个 `Array<File>` **最多 10 个文件** | "几十张原图一次塞进去"的入口不成立 | 批次化：`batch_id` + 分批上传 + 按批次处理 |
| 自定义 API 插件**只支持 GET / POST**，鉴权不自动解析 | 工具接口不能设计成 RESTful 全家桶 | 工具一律 `POST + 单一 JSON body`；鉴权自己带 header |
| 原生工作流可导出 `.jsonl` | 平台里的编排能版本化 | 导出后入 `src/agentarts/`，跟着 git 走 |
| 网页工作台不"导入"工作流 | 前端是独立部署，后端调已发布应用接口 | 前后端分离；前端不存模型密钥 |

## 六、三个分歧：我不完全同意外部方案的地方

| 分歧点 | 外部方案主张 | 我的判断 |
|---|---|---|
| 核心叙事 | 核心是"资料一致性"，画册只是副产品 | **一半同意**。一致性做内核，但初版必须仍有看得见的成品——初赛 60% 是创新性，评委只看 3 分钟视频，"数据版本管理"太抽象。折中：一致性当骨架，画册当外壳 |
| 多 Agent | 初版不要多 Agent（同意），但没讲答辩怎么写 | **还要补一层**。总决赛创新性明确列了"多 Agent 协作"，所以我们不造假多 Agent，而是写清"**为什么我们刻意不做岗位式多 Agent**"——有判断力本身就是加分项 |
| 报价 | 第一版只整理已有价格 | **同意，但保留展示形式**：报价单要能出现「区间 + 来源单据 + 改价记录」，只是不自动决策。否则 B 的价值全丢 |

## 七、风险

| 风险 | 应对 |
|---|---|
| L0 卡在插件鉴权/发布接口 | 3 天内拿不到就降级：前端直接读平台导出的结果文件，答辩时说明"在线交互版待代金券到位" |
| 工作台交互细节吞时间 | 只用现成组件库；三区固定，不加页面；图片预览用最简方案 |
| 真实素材迟迟不到 | 用"明示为模拟"的数据跑 L0–L2，L3 后用真实素材替换并重测 |
| 6 周被拉去做 PPT | 视频脚本先写、功能后做；文档复用本仓库，不另起炉灶 |
