## 生产入口和域职责

| 域 | 路由或生产调用与职责 |
| --- | --- |
| agents | 通用 Agent、任务接口和工作流编排使用 registry、runtime、contracts 和各专业 Agent。 |
| customers | 客户列表、详情页面和客户 API 调用服务，处理客户资料、别名、候选事件和评估。 |
| delivery | 通用工作台 API 和工作流页面调用服务生成、审阅和读取交付物。原生附件 API 使用域内 storage 解析文件。 |
| erpnext | ERPNext 状态、记录及报价草稿 API 使用 client、service 和 drafts 管理端点、校验和草稿回执。 |
| execution_plans | 工件页通过 `execution-plans.js` 消费需求下的计划历史及修订接口。API 接受创建、历史和详情请求，服务校验关联证据并生成计划响应对象。 |
| intake | 导入 API 处理来源、映射、候选和证据。requirements 与 execution_plans 复用既有请求解析、回执和错误处理。 |
| intent | 通用工作台 API 通过 parser 解析工作流目标并核对确认令牌。 |
| products | 商品页、商品查询 API 和事实还原 API 使用 query、versions、restoration 管理商品读取及版本事实。 |
| requirements | 候选起草、需求读取、修订和确认由 requirements API、service、schemas、calculations 合作。执行计划读取对应已确认需求修订。 |
| workflows | 通用工作流 HTTP 入口、页面和调度入口使用工作流准备、状态、审阅、执行与恢复能力。 |

变更集中在已有局部测试覆盖且能保留契约的执行计划调用链，其他九域用于厘清相邻职责和依赖。

| 整理前 | 整理后 | 契约保持依据 |
| --- | --- | --- |
| `plan_revision_collection` 解析并校验请求，锁内 `create_plan_payload` 再校验一遍同一份已标准化请求 | HTTP 层入口运行一次 `validate_plan_body`。锁内服务调用 `bind_plan_evidence`，只校验已确认需求修订的证据并就地冻结来源 | 原校验先于查找和锁定需求，错误优先顺序相同。校验返回新计划对象，各嵌套验证的标准化具备幂等性。证据仍先于指纹、回执和修订写入。保持相同事务锁、回执比较、修订 CAS 及异常处理。 |
| `validate_evidence_binding` 和 `freeze_source_references` 暴露为模块级名称，只有创建服务内部使用 | 私有函数 `_validate_requirement_evidence`、`_freeze_source_references` 表明分别核对需求证据及冻结来源 | 证据允许范围、数据库过滤、冻结字段和顺序照旧。仓库中原函数的唯一调用链已更新。 |
| POST 成功回执和 GET 详情分别拼装计划、需求修订、最新标记和实际状态 | 两者复用 API 私有 `_plan_response_fields`，沿用服务生成的 `actual` 字段 | 共同字段和实际状态值一致。创建 201、重放 200、处理中 202、GET 200，错误状态按原分支，成功 POST 保留 `status`。历史分页响应独立。 |

原路由、请求/响应字段、权限与 CSRF 接线、状态码、幂等与数据 schema 由现有入口和原写入路径继续提供。计划行继续按修订追加。无商用 ERP 写入。未使用的局部 `receipt_id` 已移除，收据原有读写顺序照旧。
