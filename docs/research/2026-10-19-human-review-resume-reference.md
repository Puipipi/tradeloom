# Human review application and workflow resume reference

Date: 2026-10-19  
Scope: Phase 3 task13b-facts design research. This note records the current TradeLoom contracts and the external resume principles relevant to applying typed human facts and continuing the fixed Product → Delivery workflow. It does not authorize production implementation.

## Existing TradeLoom evidence

- `workbench/workflows/validation.py` creates generic `HumanReview` candidates from persisted role results. For `product_profile`, the literal signal is stored under `HumanReview.source_conflict["source_refs"]["signal"]["missing_field"]`; product uncertainty is stored as `signal.uncertainty`. The source reference also carries workflow, batch, product, and revision identity. Candidate `item_ref` identifies the product or subtask.
- `workbench/workflows/reviews.py` saves a human submission as an envelope: `answer.response` contains the caller's JSON object, `answer.submitted_at` is service-generated, `answer.request_fingerprint` makes same-payload submission replayable, and `answer.source_refs` contains the validated source reference. A submitted receipt is historical and is deliberately replayed without revalidating later live sources.
- `workbench/workflows/orchestrator.py::_record_result` saves the full result in `WorkflowStep.output_refs.result_snapshot.result`, with `canonical_result_ref` pointing at `workflow_step:<step-id>:output_refs.result_snapshot`. It marks the SubTask `waiting_human`, completes the role step, creates review candidates in the same transaction, and transitions the WorkflowTask to `waiting_human`. Candidate persistence currently happens before the step output snapshot is assigned, so future candidates need an explicit originating `WorkflowStep` and a stable result reference that resolves after the encompassing transaction commits.
- `submit_review` currently locks `WorkflowTask`, then the batch `Task`, then related `Product` rows sorted by ID, then the `HumanReview`; provenance validation reads/locks referenced revisions and TaskFiles. It changes only a pending review into a submitted receipt and emits `human_review_submitted`. It does not apply facts or resume execution.
- `dispatch_subtask` rejects unresolved reviews and new idempotency keys for a logical SubTask that already has a prior step. The current initial dispatch creates attempt 1. Existing Phase 4 retry support appends explicit attempts, keeps historical result snapshots, and presently derives `SubTask.retry_count` from `WorkflowStep.attempt - 1`, with a maximum of three total attempts (first run plus two retries). `retry_subtask` is for explicitly retryable failures and rejects `needs_human`; it is not a human-resume API.
- `plan_task` returns the first completed `center_plan` step unchanged. `CenterAgent.plan(context, registry=None)` and `MockAgentRuntime.plan_task` are the pure planning entry points. The saved plan contains the two fixed role definitions and their dependency; do not add duplicate role rows or create a dynamic DAG.
- `Product` has six literal descriptive columns (`sku`, `name`, `category`, `material`, `size`, `color`) plus image metadata. `ProductRevision.snapshot` is JSON and immutable after insert. The existing revision helper's legacy snapshot includes those six fields plus `image_filename`; revision-only values such as `english_name` can exist in JSON snapshots. There is no editable `Product.english_name` column. Revision status/reviewer are mutable metadata, while snapshot/product/version are protected as immutable.
- The task12a/task13a reports explicitly defer fact application and recovery. Task14/15 design says deliverable generation consumes a frozen, confirmed current revision and does not create a source-incomplete review. Task16/17 documents make clear that only explicitly retryable failures qualify for the generic retry path and that old attempts must remain addressable.

## External patterns and their limits

LangGraph's interrupt documentation describes durable state keyed by a stable thread ID, typed resume input, and resuming with the same identity. It also calls out a significant behavior: the interrupted node starts again from its beginning, so pre-interrupt side effects can run again and must be idempotent. TradeLoom can reuse the persistence and typed-input principles, while using its existing PostgreSQL rows and transaction services rather than adding LangGraph.

The HumanLayer 12-factor-agents guidance supports making human decisions explicit, durable inputs and keeping workflow continuation under application control. These are design analogies; neither project is a runtime dependency or source of TradeLoom business policy.

References: [LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts), [HumanLayer 12-Factor Agents](https://github.com/humanlayer/12-factor-agents).

## Implications for task13b-facts

1. Keep the existing ordinary-note submission contract intact. A note remains a submitted receipt and cannot be interpreted as a literal value or approval. Typed answers must use a strict tagged schema and be shown separately in the UI.
2. Resolve the live review source from `source_conflict.source_refs`, then validate that source again at apply time. Bind each newly created review to the exact originating WorkflowStep/result snapshot; accept the legacy `subtask:<id>:output_refs.result` reference only for old receipts and only when the persisted source can still be proven. Do not silently rebind an old review to a newer result.
3. Apply one complete review cycle atomically. The request may name `review_ids`, but the service must compare that exact set with every currently pending/submitted review and require all members submitted with a supported typed response. Lock and compare every source before writing any fact; fail the whole transaction on stale source, unsupported review kind, or sibling mismatch. Merge product patches only after all compare-and-set checks pass. A successful application marks the cycle's reviews approved together and writes a separate durable apply receipt/WorkflowStep/EventLog record. It preserves the original answer envelopes and source/result snapshots. New source references always come from persisted server-side candidate records, never the client.
4. The supported literal-field allowlist is the six legacy columns `sku`, `name`, `category`, `material`, `size`, and `color`, plus `english_name`. The first six update their matching Product columns and the new revision snapshot; `english_name` is stored only in `ProductRevision.snapshot` because Product has no such column. Never infer or translate any value. Image selection, generic notes, delivery/batch review, and unknown field names remain unsupported and block the cycle.
5. `confirm_current_revision` is a distinct typed assertion for the exact current revision identified by `signal.uncertainty == "current_revision_not_confirmed"`. It is not a shortcut to confirm legacy mutable values or all batch revisions. Batch confirmation is permitted only through the explicit, clearly labelled apply-and-confirm action after all current products have valid confirmed revisions and required literal fields, including `english_name`; the action and reviewer label must be persisted.
6. Keep Product and ProductRevision coherent: after all checks, update corresponding legacy Product columns only for the six legacy fields, and store `english_name` only in each new immutable revision snapshot. Insert a new revision for every changed or explicitly confirmed product. Preserve non-edited values from the validated prior snapshot and carry source lineage. Do not fill required values by falling back to mutable Product values when the source snapshot is missing them. Derive any batch-level `Task.status=confirmed` update only from the same explicit batch confirmation and verified current-revision completeness, including any existing required `english_name` value.
7. Separate human-resume execution numbering from the transient-error retry budget. `WorkflowStep.attempt` should increase monotonically for each new attempt of the reused logical SubTask; `SubTask.retry_count` should increase only for explicit retry claims and stay bounded at two. Human resume neither spends nor resets that retry budget. Preserve legacy stored retry counts without recomputing them; fix current code that derives the counter from `attempt - 1`. Preserve the ordinary retry cap of one initial attempt plus two explicit retries, while allowing a later human-resume attempt to make the global Step attempt exceed three. Update the UI remaining-retry notice to use `retry_count`, not `attempt`.
8. Add a new `center_plan` attempt with a new idempotency key and append its plan/source snapshot; never overwrite the old center plan. Because facts alter both role inputs, refresh inputs for the exact existing two `SubTask` rows and queue both roles in their fixed dependency order; do not duplicate role rows. Any selector reading the current center plan must choose the newest applicable saved plan while historical readers can still address old plan IDs. The apply Step remains immutable after commit; the one-use resume authority is recorded on the new dispatch Step that claims it, bound to the apply Step ID, expected prior Step, input fingerprint, and latest-attempt CAS. Do not weaken the general prior-step rejection or use `retry_subtask` for a human answer. Keep all old completed Step result snapshots. Resume must re-check that the origin step remains the latest applicable needs-human result, the review cycle has been applied, no unresolved review remains, current revisions and dependencies are valid, and the fixed plan still contains exactly those two roles.
9. Keep application and continuation explicit and auditable. The apply operation must be idempotent by key/fingerprint and return the original receipt on exact replay; a conflicting payload or stale source returns conflict with no partial writes. In that transaction, prepare the new plan, refresh/queue the existing role rows, and transition `waiting_human → running` with `current_step=product_profile`. The existing “execute next step” action later dispatches the Product role; no handler or file work occurs inside apply. Delivery generation, delivery approval, and workflow completion remain separate operations.

## Open compatibility points for implementation review

- The current `retry_count` is updated as `max(retry_count, attempt - 1)` in both success and failure recording. This batch must correct that coupling: preserve legacy stored retry counts without recomputing them, increment only on an explicit retry claim, and audit eligibility, fencing, serializers, and UI remaining-retry calculations.
- Current review candidate persistence has no explicit `WorkflowStep` argument, and old `result_ref` values may identify a SubTask result rather than an immutable step snapshot. New candidates must bind a real origin Step and validation must prove it belongs to this workflow/SubTask, is the latest applicable Step, and contains the saved `needs_human` snapshot. Legacy submission replay stays compatible, but application must reject old receipts when no immutable origin Step can be proven; never fabricate a Step.
- Existing current revision checks in the submit path validate saved references, but apply requires a single deterministic lock set for all sibling reviews, Products, revisions, and referenced TaskFiles. The exact ordering must be checked against every existing product update/confirmation path before coding to avoid deadlocks.
- Existing status helpers allow `ProductRevision.status` and `reviewer` changes while keeping snapshots immutable. Apply-and-confirm creates the new current revision in `confirmed` state with the explicit reviewer in the same transaction; tests must ensure no intermediate state escapes.
- Current preparation serialization and `plan_task` select the first saved center plan; both must select the newest applicable plan while preserving historical plan IDs and snapshots.
